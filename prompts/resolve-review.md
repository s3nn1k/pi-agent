Разбери замечания ревью в MR **$@** (iid или URL; без аргумента - спроси). Действия - по
скиллу git-workflow. До фактических правок - отчёт мне на решение; изменения только после
явного аппрува. Аппрув правки = сразу и ответ `Поправил` в её треде; треды не закрываем -
резолв за ревьюером; отдельных переключателей нет.

## Триаж (каждое замечание)

| Класс           | Действие                                               |
| --------------- | ------------------------------------------------------ |
| Правка          | предложить правку кода по доменному скиллу             |
| Вопрос          | без правок и без ответа - "на решение"                 |
| Меняет норму    | цитата действующего правила канона + предложение диффа |
|                 | канона (переписать правило под замечание) или репо-    |
|                 | правки под канон; всегда - "на решение" мне первым     |
| Новая норма     | паттерн, который канон ещё не покрывает и повторится   |
|                 | без правила: вместе с правкой кода - предложение       |
|                 | нового правила (скилл, секция, формулировка); "на      |
|                 | решение" мне первым                                    |
| Спор/вне скоупа | не трогать - "на решение"                              |

Контекст замечания: position -> файл:строка; текст читать вместе с файлом, не по одной
строке.

Формулировка нового/переписанного правила канона - принцип, не симптом: покрывает все
сценарии, которые представляет частный случай замечания (канон harness-authoring).

## Отчёт на аппрув (до правок)

Таблица: замечание (n-id, файл, суть) -> класс -> предложение (дифф-набросок для правок;
для нормы - цитата + дифф канона или формулировка нового правила). Блоки "на решение":
вопросы, споры, синк канона. Жду явный аппрув.

## После аппрува

Правки и ответы в тредах - по скиллу git-workflow.

## Финал

Отчёт: что сделано (замечание -> правка -> отвечено), "на решение" без изменений, дифф
синка канона.
