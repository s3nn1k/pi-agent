# Git-workflow: операции с побочными эффектами

## Применимость

Любой стек: правила про репозиторий, не про язык. Контент правок (код, тесты, доки) -
доменные скиллы; этот - про git-операции вокруг них.

## Эталон

Рабочее состояние репо:

```
sync    = origin догнан; base свежая (HEAD..origin/main = 0, либо осознанный rebase)
дерево  = чистое между шагами (git status --porcelain пусто)
ветка   = feat/<domain>-<slug>, сверена с задачей
сессия  = единственный пишущий агент на cwd
коммит  = type(scope): суть на английском
сдача   = ветка запушена, MR создан; мерж и теги - человек
```

Роли (операция -> кто):

| Операция                                     | Агент                    | Человек             |
| -------------------------------------------- | ------------------------ | ------------------- |
| Коммит на своей ветке                        | да                       | -                   |
| Пуш своей feature-ветки                      | да                       | -                   |
| Создание MR                                  | да                       | -                   |
| Ревью и мерж MR                              | -                        | да                  |
| Резолв тредов ревью в MR                     | -                        | да                  |
| Теги (любые namespace)                       | имя + готовые команды    | да - после мержа MR |
| Rebase                                       | предлагает; по поручению | решает              |
| Push в main/чужие/теги                       | никогда                  | -                   |
| Запуск manual CI-джоб / retry / web-пайплайн | -                        | да                  |

## Реестр правил

### Гигиена

### Синк, ветка, коммит

- **R-1** Дерево чистое перед правками и между шагами; uncommitted-изменения -> стоп,
  спросить; не stash и не reset самостоятельно.
- **R-2** Sync = `git fetch` + `git pull --ff-only`; non-fast-forward или конфликт ->
  стоп, спросить.
- **R-3** Существующая ветка: сверить с задачей (`git log main..HEAD --oneline` +
  `git diff main...HEAD --stat`); посторонние правки или не совпадает -> стоп, спросить.
- **R-4** Диапазон изменений ветки = `<base>...HEAD` от merge-base
  (`git merge-base HEAD <base>`).

### Ветки

- **R-5** Ветка фичи: `feat/<domain>-<slug>`; от main, одна фича - одна ветка.

### Сессии

- **R-6** Один пишущий агент на cwd; read-only параллельно - ок. Вторая пишущая задача в
  том же репо - git worktree (у каждой задачи свой cwd) или стоп-вопрос человеку. Аномалии
  (HEAD уехал, дерево изменилось без твоих правок, чужие коммиты на ветке) -> стоп,
  спросить. Параллельные фичи = ветки; две фичи одновременно = два worktree.

### Свежесть базы

- **R-14** Гейт свежести - перед каждым новым коммитом, а также на старте/возобновлении
  работы на ветке (до правок) и при аномалиях (push отклонён, HEAD/дерево уехали).
  Проверка: `git fetch` -> `git rev-list --count HEAD..origin/main`; `0` -> ок; `> 0` ->
  предложить человеку `git rebase origin/main`; конфликт при rebase -> стоп, спросить;
  после успешного rebase - fmt/lint/затронутые тесты заново (main мог изменить контекст),
  пуш `--force-with-lease`.

### Коммиты

- **R-13** Формат `type: суть` / `type(scope): суть`; типы
  `feat|fix|refactor|tests|ci|chore`; суть - краткая, строчными, на английском, "что
  делает коммит" - и только это. Без мета-довесков: ссылок на номера правил (R-ID), имён
  конкретных скиллов, путей и имён файлов, MR-ID, номеров раундов, provenance ("по
  замечанию", "after rebase"). Общее слово canon - допустимо, когда это суть
  (`align to canon`). Тривиальные однострочники (`review fixes`, typo) - без type.
  Merge-коммиты (GitLab-авто) - не трогаем.

### Merge-request

### MR и замечания

- **R-15** MR создаёт агент. Заголовок - как коммит (R-13, eng). Тело - на русском: что
  сделано, пунктами (реализовано / тесты / миграции / breaking); формулировки и объём -
  общий канон стиля текстов. Изменения = только изменившееся относительно base;
  перенесённое из base без изменений (блок "как на main был") не пересказывать. В теле -
  только итог-изменения; процесс реализации - никогда: раунды ревью и аппрувы ("APPROVED
  после fix-раундов"), происхождение решений ("как решено", "по решению человека"),
  результаты валидаций, "требует ручной проверки", риски, стек-заметки ("после мержа уедет
  в main") - всё это в сообщение сдачи человеку, не в MR. В репо есть шаблоны MR - тело по
  R-24. Мержит человек после ревью.

  ```text
  Title: feat(orders): add documentType/documentNumber to ClientMetadata

  - поля documentType/documentNumber в ClientMetadata (OpenAPI + модель + репо)
  - покрытие functional-тестами (создание/обновление/получение)
  ```

- **R-24** Шаблон MR - из репо, до создания: `.gitlab/merge_request_templates/` читается
  из локального чекаута ветки. Выбор: интеграция с внешним шлюзом/сервисом - шаблон
  интеграции; остальное (фича, рефакторинг, доки, CI) - дефолтный. Шаблонов в ветке нет
  (не доехали в base) - тело по R-15. Заполнение: кратко, по существу; разделу нечего
  сказать - удалить его целиком; подсказки-комментарии (`<!-- -->`) можно не трогать - не
  рендерятся. Строки quick actions (`/label ~...`, `/reviewer @...`) из шаблона - оставить
  в теле: GitLab исполняет и вырезает их при создании MR (в т.ч. через API/glab), флаги
  `--label`/`--reviewer` не дублировать. Создание: заполненная копия шаблона подаётся
  через `glab mr create --description-file <file>`.

- **R-25** Репо с UI-кодом и дифф затрагивает UI-слой (компоненты, страницы, стили) -> в
  теле MR секция "Скриншоты": по скрину на изменённый экран/компонент; смена существующего
  вида - до/после. Источник - тулинг репо (e2e/storybook/ скриншот-команда); нет тулинга
  или скрин локально не снять - секции нет, причину сказать в сообщении сдачи человеку.
  Заливка - project uploads API тем же токеном, что glab (R-16); markdown из ответа - в
  тело MR; скрин-файлы не коммитятся - живут только в uploads проекта:

  ```sh
  glab api "projects/<ns>%2F<repo>/uploads" -F file=@<screenshot.png>
  # -> {"markdown":"![screenshot](uploads/-/system/...)"} -> секция "Скриншоты"
  ```

  Не-визуальные правки фронтенд-репо (deps, ci, форматирование) - без скринов.

### Токены и CLI

- **R-16** Токены git-хостов - read-only vault-стор через helper `git-cred-read` (per-host
  `credential.helper`); где физически лежит стор - деталь окружения: не искать и не
  парсить. `git fetch`/`push` по https уже авторизованы - ничего не настраивать. Токен для
  CLI/API (glab: `GITLAB_TOKEN` + `GITLAB_HOST`; gh: `GH_TOKEN`) доставать канонически -
  через сам git, не копая "где аутентификация":

  ```sh
  printf 'protocol=https\nhost=gitlab.example.com\n\n' | git credential fill
  # -> password=<токен>
  ```

  CLI не установлен - API хостинга тем же токеном (curl) или remote-подсказка из вывода
  push (GitLab печатает ссылку создания MR).

### Ревью-цикл MR

- **R-17** Обработка замечаний: правки - в те же ветки MR; отдельный fix-коммит
  (`fix`/`ci`, не amend); пуш. Объём валидации правки - канон домена/оркестрации, не
  гит-канон.
- **R-18** Решение "правим" (принятое человеком) = ровно один сценарий: правка запушена ->
  ответ "Поправил" (reply в discussion `discussions/:id/notes`, НЕ MR-level нота); в т.ч.
  повторные замечания - цикл заново. Ответ - ровно слово "Поправил", без пояснений: что
  изменено, видно в диффе. Других ответов агент не пишет вообще: вопрос, спор, "меняет
  норму" (R-19), вне скоупа - отвечает только человек. Треды агент не резолвит никогда -
  ни после ответа, ни повторно: resolve/close discussion - контур человека (ревьюера),
  тред остаётся открытым до его вердикта. Ответ - частью того же цикла правок, не
  отдельным шагом по напоминанию.
- **R-19** Замечание, меняющее норму -> всегда сначала человеку; норма синка - скилл
  harness-authoring. К человеку: цитата действующего правила + предложение (дифф канона
  или правка репо под канон); правка - после явного аппрува, канон синкается в том же
  цикле.
- **R-21** Замечания ревью в MR: одно замечание = одна line-анкорная дискуссия (SHA из
  `diff_refs`); нет дифф-строки - нота с префиксом `файл:строка`. Тело = суть (что не так
  и почему) + блок "Как поправить:". Без меташума: метки приоритета, номера правил (R-ID),
  упоминания канона/скиллов, имена инструментов и их команды - не пишем; адрес несёт
  анкор, аргумент - код репо; "Как поправить:" указывает каноничную цель репо
  (make-таргет) или нейтральный шаг ("прогнать штатный SQL-форматтер"), не команду
  инструмента. В MR - только фактические правки этого MR; отложенное (легаси, вне скоупа,
  долг), вердикты и приоритеты - в сообщении человеку, не в MR.
- **R-22** Замечания собирает агент:
  `glab api projects/<ns>%2F<repo>/merge_requests/<iid>/discussions` (аутентификация -
  R-16). Разбор нот: system - мимо; в работу - unresolved с автором != я; новая нота того
  же автора в треде, где уже отвечал, - повторное замечание (цикл R-18 заново).

### Теги

### Релизные теги

- **R-7** Теги создаёт и пушит человек: тег живёт после мержа MR (ревью) - вне цикла
  агента. Агент: рассчитать имя по конвенции, проверить свободность и коммит, выдать
  готовые команды. Исключение - явное поручение человека в текущем сообщении: выполнить
  ровно его.
- **R-8** Два namespace: корневой `vX.Y[.Z]` - релиз репо; пакетный `<path>/vX.Y.Z` -
  версия вложенного публикуемого пакета, `<path>` = путь к пакету в репо (Go-модуль:
  `pkg/service-cascade-client/v1.124.0`). WHY: тег с префиксом пути - единственный адрес
  версии вложенного пакета; без него потребитель получает псевдоверсию/SHA
  (`v0.0.0-20260819-...`). Namespace изолированы префиксом: нумерация у каждого своя,
  пересечения и обгоны легальны, стиль единый.
- **R-9** Пакетный тег: `v` + ровно три компоненты. Корневой - по конвенции репо.
- **R-10** Следующий номер = bump от max своего namespace:
  `git tag --list '<path>/v*' | sort -V | tail -1`; свободность на origin:
  `git ls-remote --tags origin '<tag>'` (пусто = свободен).
- **R-11** Тег любого namespace - на merge-коммит, уже попавший в `origin/main`, не на tip
  feature-ветки. Типовой инстанс - пакетный тег: вне main он не адресуем потребителю
  (R-8).
- **R-12** Пуш - только текущей рабочей ветки. Никогда: `main`, чужие ветки, теги,
  `--tags`, `--all`, `--force`. Исключение: `--force-with-lease` на своей ветке после
  rebase (R-14).
- **R-20** CI-джобы агент не прожимает: manual gate-ы (docker-build, deploy:*), retry,
  web-пайплайн через UI/API - контур человека, как мерж и теги. Валидация CI-конфига -
  `ci/lint` API с `dry_run` (без побочных эффектов), не запуском пайплайна. Read-only
  статус (GET pipelines/jobs) - допустим по делу (подтвердить факт для отчёта после пуша);
  фоновый поллинг - нет.

| Сдал ветку / валидирую CI                   | R-20                   |

## Workflow

Гейты (команды - в правилах реестра): `git status --porcelain` (пусто), `git fetch` +
`rev-list --count` (0 или rebase-предложение), `sort -V | tail -1` (max тега), `ls-remote`
(свободность), повторный GET discussions (в каждом поправленном треде доставлен ответ).
Точка сдачи: команды тега - в сообщении человеку, не в терминал.
