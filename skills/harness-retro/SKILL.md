# Ретро харнесса

## Применимость

Разбор конкретного сбоя с предложением минимального изменения или выводом, что менять
харнесс пока не требуется. Источник - наблюдение из задачи, не желание добавить правил.

## Эталон

```text
Сбой:               ожидали / получили
Доказательство:     источник + минимальный фрагмент
Причина:            подтверждена / гипотеза / неизвестна
Существующая норма: есть и доставлена / не доставлена / отсутствует / неизвестно
Решение:            изменить / оставить / собрать данные
Предложение:        один минимальный дифф + класс сценариев
Проверка:           случаи + критерий успеха + бюджет + риск регрессии
Статус:             не проверено / локально подтверждено / неубедительно / отклонено
```

## Реестр правил

### Диагностика

- R-1 Ожидаемое поведение подтверждай требованием пользователя, контрактом или действующей
  нормой. Наблюдаемое - конкретным действием или результатом агента. Неподтверждённое
  отмечай как гипотезу.
- R-2 Различай причины: неоднозначная задача, недоступный контекст, недоставленная
  инструкция, нарушение известной нормы, ограничение инструмента или ошибка модели.
  Неизвестная причина - допустимый результат.
- R-3 До новой нормы проверь существующую и факт её доставки исполнителю. Собственный
  пересказ инструкции агентом не подтверждает её чтение. Уже покрытый случай требует
  исправить доставку или исполнение, а не добавить дубль.
- R-4 Источники - текущая беседа и явно выбранные материалы. Расширение поиска согласуй
  отдельно. В доказательство включай минимальный обезличенный фрагмент; чувствительный
  источник оставляй закрытым до получения безопасного извлечения.

### Предложение и проверка

- R-5 Один кандидат проверяет одну гипотезу. Обоснуй место изменения и класс сценариев,
  который оно покрывает. Частный симптом - пример, не новая общая норма.
- R-6 Для проверки укажи исходный случай, соседний сценарий и признак ухудшения. Ширина
  проверки соответствует области действия изменения; локальный успех обосновывает только
  локальный вывод.
- R-7 Сравнение вариантов использует одинаковые входные данные, начальное состояние,
  модель, режим мышления, инструменты и бюджет. Зафиксируй версии конфигурации и
  фактическую модель после маршрутизации; различия условий обозначь как ограничение.
- R-8 Бюджет проверки задаётся числом случаев, вариантов и повторов либо пределом
  стоимости. Исчерпание бюджета даёт промежуточный результат, а не обязательный выбор
  победителя.
- R-9 Различай проверку формата, анализ старой траектории и новый запуск. Первые два
  способа отсекают дефекты и поддерживают гипотезу; изменение поведения подтверждается
  новым исполнением. Один запуск не доказывает устойчивый эффект.
- R-10 Итог содержит фактический объём проверки и ограничения. Для непроведённой проверки
  статус - "не проверено"; отсутствие убедительного эффекта допускает сохранение прежнего
  харнесса.

## Каталог

| Ситуация                       | Правила       |
| ------------------------------ | ------------- |
| Неясно, где возник сбой        | R-1, R-2, R-4 |
| Хочется дописать инструкцию    | R-3, R-5      |
| Нужно проверить предложение    | R-6, R-7, R-8 |
| Нужно сформулировать результат | R-9, R-10     |

## Workflow

Гейты: сбой конкретен и доказан (R-1, R-4); существующая норма проверена до предложения
новой (R-3); один кандидат - одна гипотеза (R-5); план проверки фиксирует условия и бюджет
(R-7, R-8); статус отражает фактический объём проверки (R-10).
