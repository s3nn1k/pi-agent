# Канон авторинга конфигурации харнеса

Все артефакты харнеса - инструкция для LLM. Общая формула: **спецификация целевого
состояния + дерево решений**, не справочник и не алгоритм. Артефакт говорит, КАК ДОЛЖНО
БЫТЬ (скелет правильного результата) и даёт дерево выбора (ситуация -> паттерн); маршрут
агент строит сам под ландшафт. Компас + правила, не проводник.

## Применимость

- Новый артефакт (author) - по описанию задачи.
- Правка существующего: tighten (довести до канона; режем подачу - не содержание) или
  точечный синк (замечание ревью / новая норма).
- Ревью диффа, трогающего `skills/`, `prompts/`, `agents/`.
- Написание таска субагенту перед делегированием.

НЕ для: кода расширений/скриптов (только `.md`-конфигурация); доменных скиллов (Go,
деплой) без задачи на правку их канона; запуска субагентов (нативная механика харнеса).

## Эталон

Общий скелет - 4 вопроса по порядку; конкретный формат каждого артефакта - в его
reference:

```text
Q1 ЗАЧЕМ/КОГДА   -> Применимость: триггер + границы (когда сосед, не ты)
Q2 КАК ДОЛЖНО    -> Эталон: скелет результата, модель достраивает форму
Q3 НОРМЫ         -> Реестр правил: плоский пронумерованный R-1..R-N
Q4 ГЛУБИНА       -> references/ по требованию, без формулировок правил
```

Три модели содержания (жанрозависимы): convention/target-state (~60%: Эталон + Реестр +
Каталог), workflow-гейты (~20%: тулзы + точки корректности, не хребет для craft),
reference-справочник (0% в основном файле, 100% в references/). Развёрнуто -
`references/models.md`.

## Реестр правил

- R-1 Target-State Spec + Decision Tree. Хребет - Эталон + Каталог (Каталог - при
  неоднородном выборе конструкций; в craft-скилле с однородным доменом дерево выбора
  держит группированный реестр); не справочник и не алгоритм. Procedure-as-spine для
  craft - anti-pattern; оркестрация (фазы, делегирование) как исключение: процедурный
  Workflow уместен.
- R-2 Телеграф, не проза. Списки/таблицы/код; проза - только когда nuance не сжать. Вода,
  вводные, риторика - вон.
- R-3 Каждое слово = сигнал. Нет "мы видим", "следует отметить", "важно понимать".
  Проверка: grep -n "мы видим\|следует отметить\|важно понимать" по файлу - пусто.
- R-4 description - триггер выбора, не конспект правил. Скилл: авто-триггер загрузки
  ("используй, когда..." + охват + "НЕ для..."). Промпт: "что делает" для autocomplete.
  Агент: широкий триггер роли ("что делает", не "помогает"; рецепт оркестрации - не тут).
  Правила/механики - в тело. "НЕ для" - при наличии смежного скилла или частого неверного
  триггера; иначе границу формулирует охват.
- R-5 Эталон = скелет, не проза: дерево, code-скелет, ASCII-схема - то, что дописывают.
- R-6 Реестр - единый источник норм: все требования/запреты/краевые одним нумерованным
  списком, разбитым на смысловые блоки подзаголовниками `###` (нумерация сквозная, ID
  стабильны - R-15); короткий реестр - один блок без подзаголовников. Жанр (models.md):
  craft/нормативные - реестр обязателен; tool-скиллы и скаффолдеры - без реестра, нормы в
  блоках Эталона/Ограничений. Гейт-проверяемые правила - отдельным блоком в конце с
  отсылкой к скрипту гейта; ревьюер их не проверяет. Чеклист для writer и reviewer.
  Каталог - навигация "ситуация -> R-ID", не источник правил. Дубли схлопываем;
  отказ/краевой случай = строка "триггер -> эталон". Фиксированный preamble реестра
  (механика чтения: единый источник, ID стабильны/R-15, absence-клауза/R-8, per-rule
  прогон) - допустим, не правила. Проверка: правила вне реестра (Топ-правила /
  Что-НЕ-делать / Краевые) - пересобрать.
- R-7 Progressive disclosure: правила - сразу (тело читается целиком за один read);
  глубина живёт в references/ по требованию, без формулировок правил, ссылки на R-ID.
- R-8 Absence-правила - с клаузой `Проверка:` (как перечислить кандидатов grep-ом);
  перечисление -> оправдание каждого.
- R-9 Self-contained: именованный сервис/путь -> типовая роль; жаргон -> словарь стека;
  случайные org-зависимости не упоминать (third-party стек - можно; org-либа - предмет
  канона скилла - именуется полностью); внешние скиллы не упоминаются - скилл
  самодостаточен: границы соседей описываются словами (что сосед покрывает), не именами;
  чужие R-ID/внутренности и промпты - нет. Проверка: grep -E
  `\(R-[0-9]+(/[0-9]+)* [a-zа-яё-]+\)` по промптам и скиллам - пусто (ссылка на чужой
  реестр); grep -E `R-1\.\.R-[0-9]` - пусто (диапазон, выдающий себя за весь реестр, -
  заменяется словами "весь реестр"; под-диапазоны навигации по существующим ID допустимы);
  строка с чужим именем скилла и R-N - перечисли и оправдай.
- R-10 Согласованность со смежными: не противоречат; дубль - отошли к соседу; расхождение
  допускается только при разных доменах, с пометкой границы.
- R-11 Single source: канон в одном месте; references расширяют, не пересказывают.
- R-12 Один reference = одна тема; > ~250 строк - дробить.
- R-13 Поверхность `.md` - prettier (90), ASCII-пунктуация, таблицы без ячеек-абзацев.
- R-14 Расположение: скиллы `~/.pi/agent/skills/` (глобально) / `.pi/skills/` (проектно),
  `~/.agents/skills/` (harness-agnostic); механизмные скиллы ролей - `skills-role/` (вне
  дискавери, видны только через `skillPath` агента); промпты `~/.pi/agent/prompts/` /
  `.pi/prompts/` (non-recursive); агенты `~/.pi/agent/agents/` / `.pi/agents/` (project
  перекрывает user, builtin-имя тоже). Канон-репо подключается каталогом через
  `settings.json` (`skills`), не симлинками - симлинк на внешний репо в дотфайлах =
  внешняя зависимость. Новый - рядом с соседними того же вида.
- R-15 ID правил стабильны: не перенумеровывать; новый ID = следующий номер, размещение -
  в смысловой секции (гейт-проверяемые - в гейт-блоке).
- R-16 Канон правит `.md`; контент `scripts/` - правилами стиля кода, не этот канон.
- R-17 Tighten режет подачу, не содержание: Эталон/Каталог/правила/краевые остаются;
  unsure-что-важно - оставляем.
- R-18 Изменение нормы канона - из любого источника (замечание ревью, инцидент, ретро,
  новая норма из задачи) -> сначала человеку (цитата правила + предложение диффа канона
  или репо-правки под канон); правка после аппрува; канон синкается в том же цикле.
- R-26 Правило канона - принцип, не симптом: источник (замечание ревью, инцидент, кейс)
  даёт частный случай - формулировка покрывает все сценарии, которые этот случай
  представляет; частный случай в теле правила - пример, не граница. Гейт: у нового правила
  назван класс сценариев, не только кейс-источник.
- R-19 Граница скилл/промпт - по переиспользуемости, не по механизму вызова. Строка,
  нужная другой задаче (доступ к внешней системе, справочник API, канон вида артефакта) -
  скилл; строка про этот объект/маршрут (константы задачи, фазы, апрув-стопы, контракт
  сдачи) - промпт. Мерило - принадлежность capability, не факт повтора: единственный
  потребитель сегодня не запирает знание в промпте. Команда-обёртка над скиллом допустима
  (вход задачи), знание живёт в скилле; ссылка - по имени (R-9).
- R-20 Гейт-скрипты скилла (`scripts/`): вынос детерминированных проверок реестра - от 5
  проверок; меньше - оставлять правилом в скилле (нативнее, агент подхватывает быстрее).
  VIOL - только точно детерминированные паттерны (одинаковый дифф - одинаковый вердикт);
  эвристики для VIOL запрещены - только класс CHECK (перечисление -> оправдание в отчёте).
  Скрипт печатает R-ID; тела правил живут в реестре (блок "Гейт-проверяемые", R-6),
  скрипт - только механика.

### Слои и границы

- R-21 Capability - слоями: знание "когда/зачем" - скилл (Layer 2); тонкий инструмент -
  только когда модель должна звать его с параметрами (JSON-схема в каждом запросе -
  eager); механика без параметров - CLI/скрипт через bash (ноль schema-стоимости).
  Нативный `registerTool` (structured-параметры, TUI-рендер) vs внешний CLI - выбор по
  токенам vs UX; оба живут под одним скиллом.
- R-22 Поведенческие ограничения - в ядре конфигурации (tools-allowlist, modes, субагенты;
  per-task пул, не общий котёл), не в тексте скилла: скилл - промпт, он не режет
  возможности агента.
- R-23 Ограничение != sandbox: allowlist/гейт режет запросы к инструментам, но не
  изолирует исполнение и не держит prompt-injection. Untrusted код и unattended-работа -
  контейнер/VM/micro-VM (read-only mounts, минимум кредов, сеть отрезать); внутри процесса
  настоящих границ нет.
- R-24 Поверх универсального реестра стиля - специфика репо харнеса: гейт `make lint`
  (Prettier in-place JS/TS/JSON/MD + typecheck `tsc`, падает при ошибках); канон
  форматирования - Prettier, 2 пробела, double-кавычки; исключения - `.prettierignore`
  (бандлы, `models.json`, helm-канон, рантайм `settings.json`); инструменты ставит
  `make init` (`package.json`).
- R-25 Видимость скилла - по потребителю знания: нужен оркестратору (routing, решения,
  написание) - `skills/` (личное) или канон-репо (командное); нужен только узкой роли как
  механизм исполнения - `skills-role/` + `skillPath`-байндинг агента роли, main его не
  видит и не несёт в контексте. Сигнал к role-binding: операция скилла генерит тяжёлый
  побочный вывод - объём должен съесть контекст ребёнка, не main.

## Workflow

Гейты (author и tighten):

1. Скоуп: вид артефакта (каталог), режим, расположение (R-14).
2. Согласованность: `ls` + `grep` по descriptions смежных того же вида; прочитать.
   Конфликтов/дублей нет.
3. Сначала target state: Эталон -> Каталог -> Реестр -> Workflow-гейты -> references.
4. Self-check: скелет для достраивания? Каталог покрывает выбор? Артефакт демонстрирует
   принципы, которым учит? (мета-гейт: этот скилл - эталон.) Новые правила - принцип, не
   симптом (R-26).
5. `make lint` + `git diff` -> человеку; коммит - человек.

## Где глубже

- `references/models.md` - три модели содержания и доли.
- `references/skill-canon.md` - скелет SKILL.md и специфика скиллов.
- `references/prompt-canon.md` - формат промпт-команды, аргументы, жанры тела.
- `references/agent-canon.md` - frontmatter агента, fresh/fork, тело = поведение.
- `references/subagent-task.md` - канон таска субагенту.
- `references/stack.md` - состав стека харнеса.
