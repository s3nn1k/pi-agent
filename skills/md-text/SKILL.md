# Markdown-документ: поверхность текста

## Применимость

Любой .md, который читает человек: документ, README, CONTRACT, файл скилла/промпта.
Структуру/скелет артефакта держит его собственный канон; md-text - только поверхность. НЕ
для кода, комментариев, конфигов - это не markdown-проза.

## Эталон

Скелет правильного .md - то, что дописывают (поверхность; структуру диктует канон
артефакта):

````markdown
# Заголовок

## Секция

Проза укладывается к 90; каждая строка переноса начинается со слова, не с маркера
списка. Пунктуация ASCII: тире - и --, кавычки "...", стрелка ->, многоточие ...

- пункт списка: значение - короткая фраза, не абзац

| Колонка | Колонка |
| ------- | ------- |
| id      | путь    |

```go
fmt.Println("код - в fenced-блоке с языком; содержимое синтаксически валидно")
```
````

Ширину и переносы держит форматтер; реестр ниже - то, что форматтер не чинит.

## Реестр правил

### Ширина и переносы - форматтер

- R-1 Переносы прозы и код в блоках не выставляй руками - прогоняй nvim headless-батчем
  (тот же пайплайн, что срабатывает на сохранении в nvim): проза -> жадный перенос к 90,
  fenced `go`/`sql` -> `gofmt`/`sql-formatter`, `json`/`jsonc` -> prettier без
  trailing-запятых; непарсимый блок (псевдо-код с `...`) остаётся как есть.

  ```sh
  nvim -n --headless ФАЙЛ... +'argdo w' +qa 2>/dev/null
  ```

  Нет nvim - не форматируй и скажи об этом пользователю: канон живёт в nvim-пайплайне
  (prettier-флаги не покрывают код-блоки, а без `--embedded-language-formatting off`
  prettier калечит примеры: jsonc-запятые, отступы).

  Headless-прогон сохраняет файл молча и при ошибке форматтера - ошибка видна только в
  conform.log. Проверка: смещение лога до прогона (`wc -c`) -> после прогона хвост
  (`tail -c +N`) без `ERROR`; json-блоки - json.loads по каждому.

- R-2 Хвост абзаца/пункта может быть коротким - норма, не дотягивай его текстом.
- R-3 Длинная строка кода в блоке (gofmt/sql-formatter строк не переносят) - неразрывное,
  не рви руками.
- R-4 Неразрывное (ссылка/URL, строка таблицы, code-block, длинный идентификатор) можно не
  разбивать - исключение из лимита ширины.
- R-5 Каждая строка переноса начинается со слова, не с маркера списка (`-`/`+`/`*`):
  продолжение, начатое с маркера, разбирается как новый пункт даже внутри абзаца.
- R-6 Построчный блок в пункте списка (кейс тестов, словарная статья): строки блока, кроме
  последней, завершаются двумя пробелами - hard break удерживает границы строк; без него
  форматтер склеивает блок в абзац и переукладывает по ширине.

### Поверхность

- R-7 ASCII-пунктуация: тире `-`/`--`, кавычки `"..."` или backtick, стрелка `->`,
  многоточие `...`, знак умножения `x`. Без длинных тире, типографских кавычек,
  глифа-стрелки, эмодзи, псевдографики - один рендер в терминале, диффе, любом viewer.
  Проверка: grep -n '[—–…→«»""]' по прозе - пусто; эмодзи, псевдографику и типографский
  апостроф - взглядом.
- R-8 Таблицы - ячейка в одну строку: короткое значение или фраза (id, путь, enum, число,
  словосочетание). Абзац или развёрнутое предложение в ячейке рвёт ширину и ломает парсер
  при переформатировании - выноси списком или блоком; вертикальную черту в значении замени
  словом или вынеси из таблицы.
- R-9 Код в fenced-блоке с языком (go/sql/json...) - синтаксически валиден; плейсхолдер
  значения - валидный идентификатор или комментарий, не `...`/`<?>`. Битый блок валит
  форматирование при сохранении в nvim (см. `:ConformInfo`): почини блок и пересохрани.
  Проверка: grep -n '<?>' по файлу - пусто (плейсхолдер `...` в коде блоков - взглядом).
- R-10 Декоративные рамки и ascii-арт ради красоты - вон. Проверка: grep -n
  '[─│┌┐└┘├┤┬┴┼═║]' по прозе - пусто (рамки из `+---` - взглядом).

### Краевые случаи

- R-11 Frontmatter-скаляры - YAML-метаданные, не проза: длинные строки допустимы (prettier
  block-scalars не переформатирует). Типовой инстанс - `description` агентов/промптов.
- R-12 Цитата из источника несёт чужую типографику -> в code-span дословно, как цитата;
  своя проза остаётся ASCII.
- R-13 Пример вывода команды с не-ASCII -> в code-block дословно (артефакт, не проза).
- R-14 Таблица неизбежно шире 100 (много узких колонок) -> оставить строкой таблицы
  (неразрывное); дробить, только если так читается лучше.
- R-15 Vault'ы `~/vaults/{work,personal}`: каждый `.md` несёт Obsidian-frontmatter (`id`,
  `aliases`, `tags`, `created`, `updated`) - независимо от способа создания. Через
  nvim-пайплайн скелет вставится сам (`aliases`/`tags` пустыми - заполнить по соседям
  папки: `aliases` - список из имени документа, `tags` - обычно `work`); созданный иначе
  (скрипт, агент, bash) - frontmatter добавить тем же шаблоном до сдачи; при правке
  содержимого - обновить `updated`. Проверка: `head -2 <файл>` - первая строка `---`;
  пачкой: `for f in <глоб>; do head -1 "$f"; done`.
