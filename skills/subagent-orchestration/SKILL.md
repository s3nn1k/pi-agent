# Оркестрация субагентов

## Применимость

- Решение делегировать принято (критерии - глобальный AGENTS.md); здесь - класс задачи
  (диспетчер) и какой workflow вести.
- Библиотека устоявшихся паттернов: разовый флоу остаётся в чате, в канон не идёт.
- Кому что доверить, в каком контексте и сколько раз; механика вызова - скилл
  `pi-subagents`.

## Диспетчер

Класс задачи - до первого запуска, по прогнозу диффа (риск x размер), не по ключевым
словам домена; объявляется первой строкой разметки (R-18). Класс задаёт маршрут (Каталог)
и бюджет (R-19).

- **S** - малая правка: <= 2 файлов, локальный эффект, без контракта наружу, миграции,
  правок денег/доступа. Типовой инстанс: конфиг, текст, CI, deps-бамп, точечный фикс.
- **M** - средняя: один домен, новая логика или 3+ файлов; контракт наружу только
  аддитивный (новое поле/эндпоинт без смены поведения существующих потребителей).
- **L** - риск: смена поведения существующих потребителей, необратимые данные (миграция),
  инварианты денег/доступа, кросс-доменные изменения; фича со спекой.
- **X** - вне конвейера: ресёрч, миграция инструментария, эксперимент. Маршрут свободный;
  минимум - один writer (R-6) и гейт перед MR, если тронут код.

Артефакты фичи (doc/plan/tests) обязательны только для L; M - план в таске; S - задача
текстом, артефактов нет.

## Эталон

Роль × контекст × модель:

| Роль                           | Контекст (fresh/resume)             | Модель                                  |
| ------------------------------ | ----------------------------------- | --------------------------------------- |
| worker - генерация по канону   | resume в рамках фичи (R-1)          | workhorse (R-17)                        |
| reviewer - контроль канона     | resume в рамках фичи (R-1)          | workhorse (R-17) + structured verdict   |
| adversarial - атака            | resume сопровождает фичу (R-1, R-9) | frontier: творческое сценарное мышление |
| scout/researcher - сбор фактов | всегда fresh: одноразовый сбор      | workhorse: enumeration без суждения     |
| media/vision - механизмы ролей | всегда fresh                        | под задачу: локальный стек или модель   |
| main - судья                   | сам оркестратор                     | frontier: вердикты, эскалации, аппрувы  |

Иерархия: фича -> задачи -> раунды. Раунд = fix-цикл внутри задачи; рез задачи - (R-4).

## Реестр правил

### Диспетчер и бюджеты

- R-18 Любая задача изменения репо - из любого входа (команда, чат, замечание MR) -
  классифицируется диспетчером до первого запуска; класс объявляется первой строкой
  разметки/сдачи. Спорное S|M -> M; M|L -> вопрос человеку; человек переклассифицирует
  словом. Проверка: у каждой запущенной задачи объявлен класс.
- R-19 Бюджет - стоп-вопрос, не запрет: ход (запуск субагента) > 25 мин - аларм
  ("завис?"), > 40 мин - стоп к человеку; S - <= 5 запусков / 45 мин, M - <= 10 запусков /
  2 ч, L - раунд <= 60 мин (капа на задачу нет). Близость к лимиту - стоп-вопрос с
  факторами: что сделано, что осталось, почему дольше.

### Границы контекста

- R-1 Resume по умолчанию: роли продолжают свой run в рамках фичи (fix-раунды, итерации,
  adversarial-сопровождение) - контекст и кэш дешевле перечитывания. Fresh - только по
  триггеру: (а) прошлый контекст мешает (сменился домен, противоречие прошлым вердиктам);
  (б) раздутый контекст дороже холодного старта; (в) нужна независимость от собственных
  прошлых выводов (спорный случай, первый взгляд adversarial на домен). Scout/researcher -
  всегда fresh: одноразовый сбор фактов.
- R-2 resume = память автора: в рамках фичи worker и reviewer продолжают свой run (resume
  по run-id из сессии оркестратора) - код и контекст задачи не перечитываются с нуля;
  канон в resumed run не гарантирован - его держит первый запуск задачи (R-13).
- R-3 Экономика повторных раундов: resumed-run платит cache-read (~в 5 раз дешевле полного
  input); fresh-запуск платит input целиком. Fresh и дробление - по необходимости, не по
  умолчанию.
- R-4 Дробление: один run воркера на задачу; задача = домен-фаза или рез, когда прогноз
  контекста не влезает в окно модели (крупная фаза - рез по слоям/сущностям). После задачи
  run не продолжается.

### Модели и надёжность

- R-5 Модель-тир по роли (Эталон); дешёвый контроль компенсируй structured verdict
  (`{verdict: APPROVED|CHANGES_REQUESTED, findings[]}`) + adversarial на большой модели;
  оркестратор парсит поле, не прозу.
- R-6 Один пишущий на cwd; read-only дети параллельно - ок; параллельная запись - только
  через worktree-изоляцию (механика - pi-subagents).
- R-7 Стоп-ответ ребёнка (ошибка делегирования, без вердикта/результата) - немедленный
  стоп цикла; вслепую не перезапускать. Стоп называет точный фикс («перезапусти со скиллом
  X») - один перезапуск с этим фиксом допустим; повторный стоп - к человеку.
- R-8 Cap fix-раундов: S - 1, M - 2, L - 3. Исчерпан, ревьюеры расходятся по одному факту
  или всплыло непроверенное архитектурное решение - стоп к человеку со списком.
- R-20 Fix-раунд валидирует затронутое: линтер + тесты изменённых пакетов, не полный гейт
  задачи; полный гейт - один раз перед сдачей/MR. LOW-замечания без HIGH/MED собираются в
  один fix-раунд, не по одному.
- R-17 Модельный тир - атрибут роли (frontmatter агента): роли исполнения и сбора фактов
  - workhorse, adversarial и main-сессия - frontier; не per-launch решение оркестратора:
    дешёвый effort пропускает чтение канона, и это лечится тиром роли, а не компенсацией
    ревью. Перенос роли на другой тир - правка конфига агента с аппрувом человека. Явная
    модель в запуске - только разовый override (провайдер лёг, эксперимент).

### Финал

- R-9 adversarial - по нетривиальности работы: дифф (риск-домен, несколько точек правки,
  новые контракты) или проработка/документ (риск-домен, новые контракты, инварианты
  денег/данных) - да; малое/тривиальное (одно место, локальный эффект) - без него:
  reviewer + main-осмотр достаточно (большой прогон на тривиальном - нагрузка без
  ценности). Если идёт: стартует после APPROVED первого среза и сопровождает фичу (resume,
  R-1; fresh - смена домена/фичи); в fix-раундах не участвует - смотрит изменившийся дифф
  после закрытия своих замечаний.
- R-10 Сдачу принимает main: собственный осмотр финального диффа, не агрегация детских
  вердиктов.

### Библиотека

- R-11 Паттерн входит в Каталог после повтора и подтверждённой эффективности; предложение
  о добавлении - в конце сдачи, добавляет человек.

### Канон в тасках

- R-12 Разрешение канона таска (worker/reviewer): явно во входе > по контексту из каталога
  скиллов (описания скиллов - routing-триггеры) > неоднозначно - спроси, не выдумывай.
  Примеры routing по домену - в паттернах.
- R-13 Канон передаётся каждым запуском worker/reviewer: параметром скилла (метаданные +
  путь в первом сообщении ребёнка) и текстом таска - полный путь SKILL.md + "читать
  целиком, references - по карте". Чтение полное - в первом запуске задачи; resume-раунды
  канон не перечитывают - он уже в контексте run; новая задача - заново. Параметр скилла -
  не доставка содержания: файл читает ребёнок, нерезолвившееся имя падает молча; факт
  запуска доставку не подтверждает (проверка - R-16). Блок реестра "Гейт-проверяемые"
  ревьюер не проверяет - его держит гейт канона, worker гоняет его до сдачи.
- R-15 Доменные SKILL.md оркестратор читает сам до первого код-воркера задачи (минимум
  SKILL.md; references - по потребности разбора ревью): без этого таск с путями не
  напишешь и ревью не разберёшь.
- R-16 Доставку канона подтверждает отчёт: строка "канон: <имя>" + зелёный гейт; список
  прочитанных путей - по запросу аудита, не каждым отчётом. Кодовая задача без канона -
  провал сдачи, повтор с явной доставкой. Самоотчёт - не доказательство; доказательство -
  дифф по канону и зелёный гейт.

### Доставка

- R-14 Реализация фичи итеративная: на сервисе не более одного открытого MR по фиче -
  следующий срез только после мержа предыдущего в main; пачки и стеки MR в одном репо не
  собираются (конвейер ребейзов и пакетное ревью дороже скорости). Треки по разным
  репозиториям параллельны - по одному открытому MR в каждом. S-задачи персональный MR не
  открывают: докидываются в открытый MR сессии этого репо; нет открытого - обычная ветка
  по первому коммиту, несколько S копятся и сдаются одним MR.

## Каталог workflow

Точка входа: тип задачи -> паттерн; состав ролей/контекстов/моделей - Эталон, инварианты -
Реестр.

| Тип задачи         | Связка                                                            | Reference                       |
| ------------------ | ----------------------------------------------------------------- | ------------------------------- |
| S (мал. правка)    | worker -> гейт -> reviewer -> main; без артефактов/adversarial    | -                               |
| M (фича/фикс)      | scout точечный -> worker -> reviewer -> adversarial -> main       | `references/pattern-feature.md` |
| L (риск-фича)      | итерации; adversarial сопровождает: ранний старт, resume по фиче  | `references/pattern-feature.md` |
| ревью ветки/диффа  | S - один reviewer; M/L - фанаут reviewer + adversarial -> синтез  | `references/pattern-review.md`  |
| chore, codemod     | worker по резам (R-4) + гейт; reviewer/adversarial - по риску     | -                               |
| research, разведка | scout-фанаут, по срезам вопроса -> синтез в main                  | -                               |
| доменный документ  | worker -> reviewer канон-вида -> adversarial замысла на L -> main | `references/pattern-doc.md`     |
| медиа, транскрипт  | media (механизм роли)                                             | -                               |

## Workflow

1. Класс задачи - диспетчер (S/M/L/X); маршрут по классу из Каталога; нет паттерна -
   собери из Эталона и предложи добавить (R-11).
2. Разметка цикла: задачи (домены/резы по R-4), роли, контексты (R-1) и модели по Эталону;
   бюджет по классу (R-19).
3. Раунд: worker -> гейт -> reviewer (structured verdict); стоп-ответ/cap - стоп
   (R-7/R-8).
4. Финал: adversarial по R-9 (L и M-риск; S - без) -> main-осмотр (R-10) -> сдача.

## Где глубже

- `references/pattern-feature.md` - маршрут полного цикла фичи.
- `references/pattern-review.md` - маршрут параллельного ревью ветки.
- `references/pattern-doc.md` - маршрут цикла доменного документа.
- Скилл `pi-subagents` - механика: запуск, resume API, worktree, async, бюджеты.
