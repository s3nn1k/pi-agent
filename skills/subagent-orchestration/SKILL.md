# Оркестрация субагентов

## Применимость

- Решение делегировать принято (критерии - глобальный AGENTS.md); здесь - какой workflow
  вести.
- Библиотека устоявшихся паттернов: разовый флоу остаётся в чате, в канон не идёт.
- Кому что доверить, в каком контексте и сколько раз; механика вызова - скилл
  `pi-subagents`.

## Эталон

Роль × контекст × модель:

| Роль                           | Контекст (fresh/resume)                 | Модель                                  |
| ------------------------------ | --------------------------------------- | --------------------------------------- |
| worker - генерация по канону   | один run на задачу; fix-раунды - resume | workhorse (R-17)                        |
| reviewer - контроль канона     | fresh на задачу; fix-раунды - resume    | workhorse (R-17) + structured verdict   |
| adversarial - атака            | всегда fresh                            | frontier: творческое сценарное мышление |
| scout/researcher - сбор фактов | всегда fresh                            | workhorse: enumeration без суждения     |
| media/vision - механизмы ролей | всегда fresh                            | под задачу: локальный стек или модель   |
| main - судья                   | сам оркестратор                         | frontier: вердикты, эскалации, аппрувы  |

Иерархия: фича -> задачи -> раунды. Раунд = fix-цикл внутри задачи; рез задачи - (R-4).

## Реестр правил

### Границы контекста

- R-1 fresh = независимость: reviewer и adversarial начинают задачу с чистого листа;
  продолженный судья якорится на прошлые вердикты.
- R-2 resume = память автора: внутри задачи worker и reviewer продолжают свой run (resume
  по run-id из сессии оркестратора) - код и контекст задачи не перечитываются с нуля;
  канон в resumed run не гарантирован - доставляется каждым запуском (R-13).
- R-3 Экономика повторных раундов: resumed-run платит cache-read (~в 5 раз дешевле полного
  input); fresh-запуск платит input целиком. Fresh и дробление - по необходимости, не по
  умолчанию.
- R-4 Дробление: один run воркера на задачу; задача = домен-фаза или рез, когда прогноз
  контекста не влезает в окно модели (крупная фаза - рез по слоям/сущностям). После задачи
  run не продолжается.

### Модели и надёжность

- R-5 Модель-тир по роли (Эталон); дешёвый контроль компенсируй structured verdict
  (`{verdict: APPROVED|CHANGES_REQUESTED, findings[]}`) + adversarial на большой модели;
  оркестратор парсит поле, не прозу.
- R-6 Один пишущий на cwd; read-only дети параллельно - ок; параллельная запись - только
  через worktree-изоляцию (механика - pi-subagents).
- R-7 Стоп-ответ ребёнка (ошибка делегирования, без вердикта/результата) - немедленный
  стоп цикла; вслепую не перезапускать. Стоп называет точный фикс («перезапусти со скиллом
  X») - один перезапуск с этим фиксом допустим; повторный стоп - к человеку.
- R-8 Cap review-раундов (типично 3): исчерпан, ревьюеры расходятся по одному факту или
  всплыло непроверенное архитектурное решение - стоп к человеку со списком.
- R-17 Модельный тир - атрибут роли (frontmatter агента): роли исполнения и сбора фактов
  - workhorse, adversarial и main-сессия - frontier; не per-launch решение оркестратора:
    дешёвый effort пропускает чтение канона, и это лечится тиром роли, а не компенсацией
    ревью. Перенос роли на другой тир - правка конфига агента с аппрувом человека. Явная
    модель в запуске - только разовый override (провайдер лёг, эксперимент).

### Финал

- R-9 adversarial - по нетривиальности работы: дифф (риск-домен, несколько точек правки,
  новые контракты) или проработка/документ (риск-домен, новые контракты, инварианты
  денег/данных) - да; малое/тривиальное (одно место, локальный эффект) - без него:
  reviewer + main-осмотр достаточно (большой прогон на тривиальном - нагрузка без
  ценности). Если идёт: всегда fresh, отдельный прогон в финале (после APPROVED ревьюера);
  в fix-раундах не участвует.
- R-10 Сдачу принимает main: собственный осмотр финального диффа, не агрегация детских
  вердиктов.

### Библиотека

- R-11 Паттерн входит в Каталог после повтора и подтверждённой эффективности; предложение
  о добавлении - в конце сдачи, добавляет человек.

### Канон в тасках

- R-12 Разрешение канона таска (worker/reviewer): явно во входе > по контексту из каталога
  скиллов (описания скиллов - routing-триггеры) > неоднозначно - спроси, не выдумывай.
  Примеры routing по домену - в паттернах.
- R-13 Канон передаётся каждым запуском worker/reviewer - включая fix-раунды и resume: и
  параметром скилла (метаданные + путь в первом сообщении ребёнка), и текстом таска -
  полный путь SKILL.md + "читать целиком, references - по карте". Параметр скилла - не
  доставка содержания: файл читает ребёнок, нерезолвившееся имя падает молча; факт запуска
  доставку не подтверждает (проверка - R-16). Блок реестра "Гейт-проверяемые" ревьюер не
  проверяет - его держит гейт канона, worker гоняет его до сдачи.
- R-15 Доменные SKILL.md оркестратор читает сам до первого код-воркера задачи (минимум
  SKILL.md; references - по потребности разбора ревью): без этого таск с путями не
  напишешь и ревью не разберёшь.
- R-16 Доставку канона подтверждает отчёт, не запуск: воркер/ревьюер перечисляет
  прочитанные файлы канона полными путями; кодовая задача с пустым списком - провал сдачи,
  повтор с явной доставкой. Самоотчёт ребёнка о его промпте - не доказательство;
  доказательство - прочитанные файлы и зелёный гейт.

### Доставка

- R-14 Реализация фичи итеративная: на сервисе не более одного открытого MR по фиче -
  следующий срез только после мержа предыдущего в main; пачки и стеки MR в одном репо не
  собираются (конвейер ребейзов и пакетное ревью дороже скорости). Треки по разным
  репозиториям параллельны - по одному открытому MR в каждом.

## Каталог workflow

Точка входа: тип задачи -> паттерн; состав ролей/контекстов/моделей - Эталон, инварианты -
Реестр.

| Тип задачи         | Связка                                                             | Reference                       |
| ------------------ | ------------------------------------------------------------------ | ------------------------------- |
| фича, нетрив. фикс | scout -> worker -> reviewer -> adversarial -> main                 | `references/pattern-feature.md` |
| мал. фича/фикс     | worker -> reviewer -> main (без adversarial, R-9)                  | -                               |
| ревью ветки/диффа  | reviewer(ы) параллельно -> синтез в main                           | `references/pattern-review.md`  |
| chore, codemod     | worker по резам (R-4) + гейт; reviewer/adversarial - по риску      | -                               |
| research, разведка | scout-фанаут fresh, по срезам вопроса -> синтез в main             | -                               |
| доменный документ  | worker -> reviewer канон-вида -> adversarial замысла (R-9) -> main | `references/pattern-doc.md`     |
| медиа, транскрипт  | media (механизм роли)                                              | -                               |

## Workflow

1. Паттерн по типу задачи из Каталога; нет паттерна - собери из Эталона и предложи
   добавить (R-11).
2. Разметка цикла: задачи (домены/резы по R-4), роли, контексты и модели по Эталону.
3. Раунд: worker -> гейт -> reviewer (structured verdict); стоп-ответ/cap - стоп
   (R-7/R-8).
4. Финал: adversarial fresh по R-9 (нетривиальные; тривиальные - сразу main-осмотр R-10)
   -> сдача.

## Где глубже

- `references/pattern-feature.md` - маршрут полного цикла фичи.
- `references/pattern-review.md` - маршрут параллельного ревью ветки.
- `references/pattern-doc.md` - маршрут цикла доменного документа.
- Скилл `pi-subagents` - механика: запуск, resume API, worktree, async, бюджеты.
