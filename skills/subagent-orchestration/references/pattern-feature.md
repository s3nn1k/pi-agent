# Паттерн "фича": полный цикл по готовой проработке

Оркестратор ведёт цикл, код руками не пишет. Инварианты (контексты, раунды, вердикты,
стопы, бюджеты) - реестр скилла; здесь - маршрут. Паттерн ведёт M (одна итерация) и L; S -
одной задачей worker -> гейт -> reviewer -> main без этого паттерна (Каталог скилла).

## Вход

Вход - папка фичи, путь к одному из `doc.md`, `plan.md`, `tests.md` (сначала разреши
соседние артефакты) или задача текстом; опционально каноны. Комплект артефактов по классу:
S - задача текстом, артефактов нет; M - план в таске, `doc.md` опционален; L - готовая
спека: `doc.md` финализирована, `plan.md` обязателен, отсутствие `plan.md` - вопрос
человеку, без тихого перепланирования. `tests.md` - только при содержательных кейсах,
пустой файл не создавать.

## Каноны фичи (домен -> скилл; объяви списком до первой итерации)

Разрешение канона и передача в таске - R-12/R-13 (routing - по каталогу скиллов сессии,
описания - триггеры; несколько канонов - списком); доменные SKILL.md грузи себе до первой
итерации (R-15). Каноны артефактов сдачи объявляй тем же списком и грузи себе сам
(субагентам не передаются): тело MR - канон стиля поверх гит-канона (шаблон MR репо,
лаконичность); UI-дифф - гит-канон (секция скриншотов); `doc.md`, `plan.md` и существующий
`tests.md` - каноны соответствующих артефактов фичи.

## Разметка - итерации и задачи (до Фазы 0)

Разметка - из согласованного `plan.md`: `doc.md` задаёт требования, существующий
`tests.md` - покрытие; здесь - сверка с репо, не построение плана с нуля. Доставка -
итерациями: каждая - рабочий срез (код среза + его тесты), свой MR; агент не мержит -
человек ревьюит и мержит, следующий срез стартует от обновлённого main. На сервисе не
более одного открытого MR по фиче - без стеков и пачек (конвейер ребейзов и пакетное ревью
дороже скорости); треки по разным репозиториям параллельны, по одному MR в каждом.

1. **Разведка** (L): scout-фанаут по `doc.md`, `plan.md`, `tests.md` и репо - зоны правки
   (точки входа, соседние паттерны, объём), покрытие по `tests.md` (что уже есть, чего не
   хватает, что допилить/убрать/добавить), тесты и гейты канона. M - один точечный scout;
   S - без разведки. Результат - факты, не решения.
2. **Сверка плана:** разметка - из `plan.md`; дополнить каждую задачу зоной правки
   (разведка) и каноном (routing: домен -> скилл). Рез задачи - R-4: прогноз контекста не
   влезает в окно воркера. Расхождение с репо - правка `plan.md`; `doc.md` менять только
   при изменении требований. Отсутствующий план на L - стоп к человеку, не тихий replan;
   M - план в таске оркестратора. Одна итерация одной задачей - без разведки, сразу к
   Фазе 0.
3. **Подтверждение:** итог сверки (зоны, каноны, резы) - человеку до Фазы 0, работа после
   подтверждения.

## Фаза 0 - подготовка репозитория

До любых правок (писатели наследуют cwd - ветка должна быть готова до первой итерации).
Подготовь репо по гит-канону сессии. Любой стоп по канону - к человеку, работу не
начинать. Отчитайся: ветка, base, чистота дерева, отставание от origin/main, результат
сверки.

## Итерации 1..N - срезы плана, каждая своим MR

Итерация стартует после Фазы 0; следующая - после мержа предыдущей в main: свежая ветка от
main, не поверх ветки предыдущей. Задачи - из `plan.md` и разметки; домен = задача,
раунды, стопы и бюджет - реестр скилла (R-1, R-8, R-19, R-20). Тесты среза - задача той же
итерации, не финальная фаза цикла.

1. **Контракт среза (M/L):** первый ход воркера - до кода, тем же run: файлы
   (создан/изменён/удалён), сущности (сигнатуры новых/изменяемых типов, эндпоинтов,
   миграций - без тел), тесты, прогноз эффективного диффа (R-21), видимые отклонения от
   плана. Оркестратор сверяет механически: каждое требование среза покрыто контрактом;
   файлы реальны по фактам разведки; прогноз в лимитах R-21 - превышение дробит задачу до
   кода, не после. Аппрув человека: L - всегда, M - при прогнозе > 200 строк; ниже -
   оркестратор сам. Отклонение от плана, всплывшее в контракте, - вопрос до кода. После
   кода - автосверка: изменённые файлы и объём диффа против контракта; чужой файл или
   превышение - стоп-вопрос, не "посмотрим в ревью".
2. **Реализация:** `worker` продолжает тот же run (контракт уже в контексте); канон домена
   и точки входа - из разметки. Требуй зелёный gate **по канону домена** - команды
   называет канон, воркер отчитывается ими и статусом; ты команды не хардкодишь.
3. **Fix-цикл:** `reviewer` со скиллом канона домена. В таске: per-rule вердикт
   (гейт-проверяемые и канон текстом - R-13).
   - `CHANGES_REQUESTED` -> мерж замечаний (синтез: блокер - одобрение человека / фикс
     сейчас / опционально / отложить с причиной) в `worker` как fix-задача: resume без
     перечитывания канона (R-13), валидация затронутого (R-20), LOW без HIGH/MED - пачкой
     в один раунд; ревью повторно - resume (R-2).
   - `APPROVED` -> домен готов; следующий.
4. **Граница домена:** файл вне канона задачи - стоп воркера и эскалация. Дефект другого
   домена, всплывший в итерации (красный тест из-за реализации) - возврат в задачу этого
   домена (правка + её ревью), не правка "под тест" здесь.
5. **Сдача итерации:** все задачи итерации APPROVED - adversarial сопровождает фичу (R-9):
   старт - после APPROVED первого среза, дальше каждый срез resume (сценарии отказа, стыки
   с предыдущими); после правок его замечаний - изменившийся дифф тем же run.
   `CHANGES_REQUESTED` -> замечания в `worker` домена + повторный `reviewer`. `APPROVED` -
   сдача по гит-канону: коммиты, пуш, MR (единственный открытый по фиче в этом репо);
   ссылку на MR - человеку. До пуша прогони чек-лист артефактов (каноны - раздел "Каноны
   фичи"): тело MR по канону стиля и шаблону; UI-дифф - по канону git-операций
   (скриншоты); артефакты фичи связаны и синхронны с решениями итерации. Далее - следующая
   итерация.

## Финал - целостность фичи

Финал - сопровождающий adversarial: resume, пока жива сессия оркестратора; после паузы
(мерж, рестарт) - fresh с его прошлыми находками из артефактов итераций и совокупным
диффом фичи от её стартового main - кросс-итерационные швы, то, что per-срезовое ревью не
видит. Признаки якоринга (спорный случай, серия "держит" по риск-точке) - разовый
fresh-прогон (R-1). `CHANGES_REQUESTED` - правка следующим срезом (worker -> reviewer ->
adversarial по изменившемуся). `APPROVED` - фича готова; мерж - человек.

## Приёмка

Сам осмотри совокупный дифф фичи от её стартового main; подтверди focused-валидацию,
связность артефактов по общему контракту и суммаризуй: разметка (итерации, задачи),
итерации (задачи, раунды, статусы, MR), adversarial-сопровождение (срезы + финал),
артефакты сдачи по чек-листу (тела MR, скриншоты, связанные `doc.md`, `plan.md`,
`tests.md` если есть), отложенное, почему цикл остановился.
