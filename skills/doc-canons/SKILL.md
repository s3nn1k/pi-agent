# Каноны доменных артефактов

## Применимость

Канон вида повторяемого доменного артефакта; один вид = один reference, правила вида живут
в нём целиком:

- **артефакты фичи** - общая структура и ссылки определены здесь; нормы вида:
  - `doc.md` - итоговая спецификация (поведение, контракты, инварианты) -
    `references/research-doc.md`;
  - `plan.md` - согласованный план доставки - `references/implementation-plan.md`;
  - `tests.md` - спецификация покрытия фичи - `references/test-cases.md`;
- **сообщение в канал product** - анонс фичи по тех. проработке -
  `references/product-message.md`;
- **разбор инцидента** - postmortem-отчёт: что произошло, почему, влияние, action items -
  `references/incident-report.md`.

Границы соседей (дубль - отошли к соседу):

- поверхность текста (ASCII-пунктуация, переносы, таблицы) - не здесь;
- конфигурация харнеса (скиллы/промпты/агенты) - не здесь;
- исполнение integration-тестов - не здесь, здесь формат кейс-файла.

## Эталон

Скелеты всех видов - модель достраивает форму; полный скелет - в reference вида:

```text
артефакты фичи                    сообщение в канал
<feature-slug>/                   🔶<Фича>
  doc.md                          <суть для читателя>
  plan.md                         🔷<Раздел> / 🔹-пункты
  tests.md (если есть кейсы)
doc.md:                          разбор инцидента
# <Тема>                          # <дата> <Имя>
- [[#Раздел]]                     ## Основная информация
## Термины                          ## Разбор / Таймлайн / Выводы
## Шаги / Логика                    ## Action Items (таблица)
plan.md:
## Итерации
tests.md:
### <область>
- happy.<суть>
  Given: <предусловия>
  When: <вызов интерфейса>
  Then: <наблюдаемый исход>
```

## Реестр правил

- R-1 Правила вида артефакта - целиком в его reference (один вид = один реестр); SKILL.md
  их не дублирует.
- R-2 Фича хранится в папке `<feature-slug>/`: обязательны `doc.md` и согласованный
  `plan.md`; `tests.md` создаётся только вместе с содержательными кейсами. Эти три
  артефакта могут ссылаться друг на друга без отдельного указания; для одноимённых файлов
  разных фич ссылка должна быть относительной Markdown-ссылкой на соседний путь или
  wiki-ссылкой с путём папки фичи, а путь и заголовок должны разрешаться. Общая структура
  и политика внутренних ссылок действуют только для артефактов фичи, не для product и
  postmortem. Пустые заготовки не создаются. Проверка: перечислить `doc.md`, `plan.md`,
  `tests.md` в изменяемых папках фич и проверить наличие обязательных файлов и
  содержательных кейсов в каждом существующем `tests.md`.

## Каталог

| Ситуация                              | Reference                           |
| ------------------------------------- | ----------------------------------- |
| Пишу/правлю `doc.md` фичи             | `references/research-doc.md`        |
| Пишу/правлю `plan.md` фичи            | `references/implementation-plan.md` |
| Пишу/правлю `tests.md` фичи           | `references/test-cases.md`          |
| Пишу/правлю сообщение в канал product | `references/product-message.md`     |
| Пишу/правлю разбор инцидента          | `references/incident-report.md`     |
| Поверхность текста любого из них      | не здесь                            |
| Исполнение тестов по кейсам           | не здесь                            |

## Где глубже

- `references/research-doc.md` - принципы содержания `doc.md` фичи.
- `references/implementation-plan.md` - эталон и реестр `plan.md` фичи.
- `references/test-cases.md` - формат кейса, id-конвенция и каталог охвата `tests.md`.
- `references/product-message.md` - каркас и содержание сообщения в канал product.
- `references/incident-report.md` - каркас разбора инцидента: шапка, таймлайн, action
  items.
