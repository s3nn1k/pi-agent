# Канон research/spec-документа

Документ читают как **готовую спецификацию**, а не как лог сессии: в нём результат, а не
процесс. Здесь - содержание; поверхность текста - по канону markdown; маршрут соавторства
(фазы, где живёт файл) - у вызывающей команды, не здесь.

## Реестр правил

- R-1 Только результат, без следов расследования. Следы - ссылки на существующий код
  (имена файлов/функций, которые читали), рабочие заметки ("уточнить"), первое лицо ("я
  проверил"); вычищаются финально. Не следы, а результат - артефакты, которые документ
  проектирует сам (контракты внешних точек - R-13, миграции/DDL, конфиги, схемы):
  оставляем как часть результата, проза вокруг них не пересказывает содержание (R-9).
  Проверка: `grep -in "уточнить\|проверил"` перечисляет кандидатов следов - каждый
  вычистить или оправдать; остальные (ссылки на имена кода, первое лицо) - взглядом.
- R-2 Логику - словами, по шагам: последовательность шагов простым языком, не "как в
  коде". Алгоритм - нумерованные шаги; независимые аспекты - короткие пункты с предметными
  подписями ("Данные", "Обновление", "Чтение"). Связное объяснение остаётся абзацем:
  единый шаблон для всех разделов не нужен. Величины/символы/термины - определение каждого
  в начале (раздел "Термины"); определение раскрывает значение, а не пересказывает
  алгоритм.
- R-3 Минимальная правка: правишь ровно то, о чём просят; смежное не трогать, "заодно" не
  причёсывать.
- R-4 Один факт - одно место: правило или инвариант полностью описан в одном разделе; в
  остальных - ссылка на него либо только отличие. Проза дополняет код/SQL/таблицу/пример,
  а не пересказывает их. Задачи ссылаются на требования, не повторяют их. Проверка: поиск
  ключевых понятий по документу перечисляет повторные упоминания -> каждое несёт
  определение, ссылку или отдельное условие, иначе объединить с основным описанием.
- R-5 Где неоднозначно - плейсхолдер "Вопрос / Ответ" (или `TODO:`), не выдумывать.
- R-6 Содержание - только по сути: постороннее (чужие окружения вроде beta/внешнего
  gateway, служебные детали не по теме) - убрать. Проверка: `grep -in "beta\|gateway"`
  даёт кандидатов постороннего - каждый оправдать; служебные детали - взглядом.
- R-7 Без скоропортящейся конкретики - того, что устареет к реализации: порядковых номеров
  и точных имён файлов миграций, путей, счётчиков, дат. Миграцию называют по смыслу,
  номер/имя ставит реализация. Проверка: `grep -in "миграци\|\.sql"` даёт кандидатов
  миграционной конкретики - каждый назвать по смыслу; пути/счётчики/даты - взглядом.
- R-8 Только текущий скоуп, без будущих доработок: описываем то, что делается сейчас.
  Будущее (деление на v1/v2, "потом добавим", дорожные карты) - отдельный документ, когда
  дойдём. Проверка: `grep -in "потом\|в будущем\|v2\|дорожн"` даёт кандидатов - каждый
  оправдать.
- R-9 Без деталей архитектурной реализации. Спека - про поведение системы (что делает
  фича: эндпоинты, модели данных, статусы, инварианты), не про устройство кода и не про
  представление данных. Раскладка по файлам/пакетам, где живут контракты/порты, wiring -
  решает реализация; физическое представление величин в контракте/хранилище (строка vs
  число, decimal vs float, обоснования точности/round-trip) задаёт канон стека сервиса -
  спека фиксирует семантику поля, не формат. Артефакты, которые документ проектирует сам
  (DDL/миграции, контракты внешних точек - R-13, конфиги, схемы), остаются - R-1.
- R-10 Доработка нескольких единиц (сервис, подсистема, слой) - блоками по единицам:
  заголовок блока = единица, сразу видно, что меняется где; правки разных единиц в одном
  разделе не смешивать.
- R-11 Ссылки на другие документы - только по явному указанию человека ("смежный
  документ", "см. ...", вики-линк `[[...]]` на другой файл); без указания документ
  самодостаточен, нужный контекст - в "Терминах". Ссылки на заголовки самого документа
  (`[[#...]]`, R-12) - не тут. Проверка: `grep -in "смежн\|см\. \|\[\[[^#]"` перечисляет
  кандидатов - каждый убрать или оправдать указанием человека.
- R-12 Оглавление - рукописный список ссылок на заголовки документа ([[#Заголовок]],
  Obsidian-стиль) сразу после интро, до "Терминов": уровни ## и вложенные ###; при
  переименовании заголовков оглавление правится руками. Копирование в Confluence: блок
  оглавления вырезается (wiki-ссылки там не живут), документ вставляется обычным paste (не
  "как текст" - иначе заголовки не сконвертируются), на странице добавляется макрос /table
  of contents. Проверка: `grep -c "\[\[#"` после интро > 0; заголовки вне оглавления -
  взглядом.
- R-13 Внешние контракты для потребителей - обязательная часть тех. раздела, наравне с
  миграциями: интерфейс, который фича отдаёт наружу. Новая точка - адрес (HTTP-ручка:
  метод + путь, напр. GET /api/v1/merchants/orders/{id}; gRPC-метод; событие/топик
  брокера) + пример тела запроса и ответа (JSON, все поля; ответ - если есть); новое поле
  в существующей точке - адрес точки + поле с примером значения, тело целиком не
  повторяем. Транспорт любой (HTTP, gRPC, брокер сообщений и т.п.) - форма примера по
  транспорту. Граница: контракты, в которые сервис сам ходит как клиент, не описываем;
  исключение - проработка межсервисного взаимодействия с доработкой нескольких сервисов:
  тогда контракт описан как внешний контракт сервиса-владельца. Адрес точки - идентичность
  контракта, не скоропортящаяся конкретика (не R-7).
- R-14 Разбивка на задачи - замыкает документ: план доставки фичи, согласовывается
  человеком здесь, реализация его потребляет. Итерации доставки - вертикальные срезы по
  зависимостям (срез = доставляемое целое: код + тесты; один MR на всю фичу - тяжёл в
  ревью); крупный домен доставки (деплой, миграции) - своей итерацией, обычно последней. В
  итерации - задачи: единица (R-10) + суть правки со ссылкой на раздел документа.
  Уровень - "что и в каком порядке", не "где в коде": зоны/файлы правки находит
  реализация. Правки содержания - пересмотр разбивки. Малая фича - вырождается в одну
  итерацию одной задачей, но раздел есть всегда.
- R-15 Компактность - меньше слов при сохранении требований. После сокращения однозначно
  понятны участник, действие, условия и результат; ограничения, исключения и гарантии
  сохранены. Проверка: сопоставить требования исходника с новой редакцией -> каждое
  сохранено; противоречия и неоднозначности переданы человеку, а не разрешены новым
  допущением.
- R-16 Согласованное дополнение встраивается в соответствующий раздел в пределах задачи;
  заменённые им формулировки обновляются. История обсуждения не становится отдельным слоем
  спеки. Проверка: поиск заголовков "Дополнение", "Amendment", "Уточнение" перечисляет
  кандидатов -> каждый встроить по смыслу либо сохранить как явно запрошенную историю.

## Пример подачи

Одинаковые требования, разная организация текста.

**До:** Кэш обновляется существующим воркером синка балансов на каждом тике, строки
создаёт только он, карточки только читают кэш без пересчёта и создания строк, а интерфейс
показывает время среза; допустима задержка до одного тика.

**После:**

- **Обновление:** существующий воркер синка балансов, каждый тик.
- **Создание строк:** только этот воркер.
- **Чтение:** карточки читают кэш; не пересчитывают и не создают строки.
- **Отображение:** время среза; допустимая задержка - один тик.
