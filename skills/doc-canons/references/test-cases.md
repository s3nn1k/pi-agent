# Канон файла функциональных тест-кейсов

Файл `tests.md` в папке фичи - спецификация покрытия, а не лог работы: писать/править сами
тесты - задача реализатора, здесь не обсуждается. Кейсы выводятся только из
финализированного `doc.md`. Здесь - содержание и формат; поверхность текста - по канону
markdown; маршрут запуска (preflight, точки фичи) - у вызывающей команды, не здесь.

## Эталон

Общая структура и жизненный цикл артефактов фичи - по общему контракту doc-canons. Этот
reference задаёт содержательный формат кейсов под заголовками областей, единой формой:

```
### Платежи

- happy.deposit.to_payout
  Given: P(target=5000, bal=1000); trader (USDT)
  When: POST /api/v1/trader/payments/deposits, amount=2000
  Then: 201; internal_wallet = P
- negative.deposit.over_limit
  Given: P(target=1000, bal=0); лимит 500
  When: POST /api/v1/trader/payments/deposits, amount=600
  Then: запрос отвергнут (превышен лимит)
```

## Реестр правил

### Файл и вход

- R-1 Размещение и жизненный цикл `tests.md` - по общему контракту артефактов фичи в
  doc-canons; этот reference задаёт только формат кейсов.
- R-2 Кейсы выводятся только из финализированного `doc.md`; неоднозначность - вопрос в чат
  до выписывания, не плейсхолдер и не выдумка.
- R-3 Термины/сущности - из раздела "Термины" `doc.md`; ссылка на `doc.md` может быть
  относительной; отдельный блок терминов в файле кейсов не дублируется.

### Формат кейса

- R-4 Единый формат - все кейсы одной формой, без смесей (никаких таблиц решений,
  authz-матриц, prose-флоу рядом); параметрические правила разворачиваются в отдельные
  кейсы - по одному на ветку/актора.
- R-5 id = `<area>.<суть>` - область в префиксе: `happy` | `negative` | `edge` |
  `idempotency` | `authz` | `lifecycle` | `concurrency` | `state` | `regression`;
  отдельного поля `area` нет.
- R-6 Given - состояние до действия; сущности - короткой ссылкой на термины спеки
  (`P(target=5000, bal=1000)`), без пошагового сетапа в каждом кейсе.
- R-7 When - endpoint + роль + ключевые поля payload.
- R-8 Then - наблюдаемый ответ И/ИЛИ side-effect (созданные/изменённые сущности, балансы,
  проводки), без механизма проверки; в одну строку, длинный - в две.
- R-9 Статус ошибки в Then - семантикой словами, не кодом: "доступ запрещён", "запрос
  отвергнут (неавторизован)", "конфликт уникальности". Какой код выставит сервис
  (401/403/400) - деталь его архитектуры (шлюз vs middleware vs биндинг хедеров), решает
  реализация. Успех (200/201) и статусы-контракт (404 "не существует", 409 "конфликт") -
  указывать можно.

### Компактность

- R-10 Между кейсами в группе пустых строк нет; кейсы под заголовками `### <область>`;
  дублирующие ветки с одинаковым исходом схлопываются в один.
- R-11 Многошаговый сценарий (типовые инстансы: lifecycle, idempotency, concurrency) -
  цепочка обычных кейсов: "следующее действие" становится `When` своего кейса; отдельных
  полей продолжения (Follow-up) нет.

## Каталог охвата

Чеклист прогнать по каждой точке фичи; каждый пункт - кейсы единого формата; не
фильтровать "уже проверялось" - покрытие считается по фиче, а не по существующему сьюту:

- **happy-path** - полный флоу до терминального статуса.
- **negative / boundary** - превышение лимита, невалидный ввод, недостаточно средств,
  нарушение инварианта -> отвергнуто с понятной семантикой.
- **idempotency** - повторный/опоздавший колбэк, повтор при терминальном статусе -> no-op.
- **authz (актор x действие)** - кто может/не может; чужой ресурс -> 404 (не раскрываем) /
  403; fail-closed. По кейсу на пару актор x действие, не матрицей.
- **state-derivation** - вычисляемые/деривированные поля.
- **side-effects accounting** - проводки/балансы/события: кто-кому-сколько, комиссии,
  курсовые разницы.
- **lifecycle transitions** - переходы статусов (created -> success / failed / expired),
  допустимые и нет.
- **concurrency / race** - двойной колбэк, webhook race, одновременные действия над одной
  сущностью.
- **regression** - известные краевые баги/инварианты из прошлого, если релевантны.
